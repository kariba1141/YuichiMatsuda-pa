ETRCARS 内部設計書

1. 概要

本内部設計書は、ETR-CARS システムの設計内容を詳細に記述し、開発者が実装するための指針を提供するものである。

本システムは、Web アプリケーションと iPad アプリケーションで構成され、統合プラットフォーム上で車検、修理、整備、および商品などの各種サービスを管理する。

設計方針
  • ドメイン境界を明確にしたモジュラーモノリス構成

バックエンドは、Django によるモジュラーモノリス（例：customers、license plates、orders 等のドメイン単位で app を分割）として構築する。

これにより、デプロイを簡素に保ちつつ、関心の分離とテスト容易性を確保する。API リソースはこれらのドメインに密接に対応させ、予測可能な契約（コントラクト）とする。

  • 非同期処理による疎結合化

長時間実行や I/O 負荷の高い処理（インポート/エクスポート、メール送信、分析等）は、Django RQ + Redis によるバックグラウンドワーカーへオフロードする。

ジョブは API により起動され、別プロセスで実行することで、リクエストの遅延を低減する。

  • ABAC によるマルチテナント（販売店/店舗スコーピング）

認証済みプロファイルの属性（dealer_id、shops 等）に基づきアクセスを制約する。全クエリに販売店/店舗スコープ（属性ベースアクセス制御）を適用し、レスポンスも呼び出し元の組織コンテキストにフィルタリングする。S3 上のファイルは dealer 単位のプレフィックスでキーを分離し、テナント間のデータ漏洩を防止する。

  • 最小権限の徹底

ECS タスクはスコープを絞った IAM ロールで実行する。S3 バケットは最小権限ポリシーおよび dealer スコープのプレフィックスを強制する。

RDS へのアクセスはアプリケーションのセキュリティグループに限定する。KMS（CMK）により秘密情報および S3 データを暗号化し、さらにアプリケーションのフィールドレベル暗号化で PII を保護する。

  • セキュリティおよび PII 保護を設計段階から組み込み

TLS（HTTPS）をエンドツーエンドで適用し、エッジで HSTS を有効化する。機微情報（電話番号、メールアドレス、住所等）はフィールドレベル暗号化（検索可能な暗号化フィールド経由で AES-256-GCM）を用いる。

パスワードは PBKDF2/SHA-256 でハッシュ化する。ログには PII を出力せず、トークン等はマスキングする。

  • 認証・認可方式の一貫性

JWT アクセストークン（有効期限 7 日）を採用し、ログアウトはステートレスに扱う。

認可はロール（Admin、Dealer Admin、Dealer Manager、Shop Manager、Shop、Tablet）による RBAC とし、エンドポイント群ごとの O/X 権限マトリクスをドキュメント化する。

UI では制限アクションを非表示にするが、最終的な判定はサーバーサイドのチェックを優先する。

  • 信頼性・リトライ・可観測性（Observability）

外部リクエスト（送信系）の標準タイムアウト（接続/読み取り）を定義し、冪等呼び出し（例：ETR）にはジッタ付き指数バックオフを適用する。

バックグラウンドジョブは上限付きリトライ（RQ の retry + failure registry）を設定する。Sentry によりエラー/性能トレースを収集し、ログは correlation ID（traceId）、ステータス、レイテンシ等を含む構造化ログとする。

  • 性能・スケーラビリティ重視

ECS Fargate + ALB により水平スケールを可能とする。リスト系エンドポイントにはデフォルトのページネーション（例：40件）を強制する。重い計算はバックグラウンドジョブで分離する。

キャッシュ（Redis）は選択的に適用し、キー設計（method + dealer/shop + params）を明確化して、陳腐化やテナント混在を防止する。

  • API ファースト（契約の統一）

REST/JSON を基本とし、ページネーション、フィルタリング、problem+json 形式のエラー形状を統一する。バージョニングによりクライアントへの破壊的変更を回避する。

  • 国際化（i18n）およびアクセシビリティ

Web は ngx-translate、iOS は端末ロケール設定に従う。UI テキスト、日付、数値は日本語/英語（JA/EN）でローカライズする。iPad 利用シーンを想定し、タップ領域やレイアウトを最適化する。

  • コンプライアンスおよびデータライフサイクル

バックアップ（RDS 自動バックアップ）、アクセスログ、インポート/エクスポートの監査証跡を整備する。データ保持および消去ポリシーは APPI（個人情報保護法）に準拠して整合させる。

本ドキュメント作成にあたり統合した資料
  • システム構成：システムの技術アーキテクチャを定義し、バックエンド構成および iOS クライアント構成を含む。
  • Web/iOS モジュール構成：各アプリケーションの高レベルなコンポーネント分割を示し、機能をモジュール単位に整理し相互関係を定義する。
  • Web/iOS 画面（インターフェース）設計：両プラットフォームの UI/UX（画面レイアウト、ナビゲーションフロー、インタラクション）を規定する。
  • Web/iOS 内部設計：各モジュールの機能要件を実現するためのアルゴリズム、ロジック、データ構造を記述する。
  • DB 設計：テーブル、項目、リレーション（ER 図）、インデックス、ストアドプロシージャ等を含む完全なスキーマを提示する。
  • API 設計：Web/iPad アプリとバックエンドサービス間の通信仕様（REST エンドポイント、リクエスト/レスポンス形式、認可等）を定義する。
  • エラーハンドリング：障害・例外・入力エラーを検知し、記録し、適切に応答するための標準メカニズムを規定する。
  • セキュリティ設計：データ暗号化/保護、認証方式、認可/アクセス制御、入力検証・サニタイズ等のセキュリティ対策の実装方針を記述する。

2. システム構成

本システムは、複数のコンポーネントが連携して動作する。

2.1. 概要

ETR-CARSシステムは、マルチプラットフォーム環境をサポートするために設計された、現代的でモジュール化されたアプリケーションである。2つの異なるクライアントアプリケーション（Web管理サイトとiOSアプリケーション）にサービスを提供する単一でスケーラブルなバックエンドAPIで構成される。

クライアント iOSアプリケーション Swift / UIKit iPadデバイス向けに構築されたネイティブアプリケーションで、最適化されたユーザー体験の提供に注力する。

2.2. Webシステム／バックエンド構成

Webサーバ／ロードバランサ：

本システムは、唯一の公開入口点としてAWS Application Load Balancer（ALB）を使用する。ALBは、すべての受信HTTP/HTTPSトラフィックを処理し、SSL終端を実行し、リクエストをアプリケーションサーバへ直接ルーティングする。また、複数のコンテナインスタンスにわたる重要な負荷分散も提供する。

アプリケーションサーバ：

Djangoフレームワークで構築されたモノリシックなバックエンドで、REST APIエンドポイントを提供する。Dockerでコンテナ化され、Fargate起動タイプのAWS Elastic Container Service（ECS）上で実行される。これにより、サーバレスなコンテナ運用が可能となる。サービスはCPUおよびメモリ負荷に基づいてオートスケールするよう設定される。

データベースサーバ：

主データベースとしてAmazon RDS for PostgreSQLを使用する。マネージドサービスとして、自動バックアップ、パッチ適用、高可用性を扱う。

ワーカーシステム：

非同期タスクはDjango-RQによって管理される。メッセージブローカとしてAmazon ElastiCache for Redisを使用し、バックグラウンドジョブを効率的にキューイングおよび処理する。

ストレージ：

Amazon S3（Simple Storage Service）が、すべてのメディアファイル（ユーザーアップロード）および収集された静的アセットの保存に使用される。Djangoアプリケーションは、既定のファイルストレージバックエンドとしてS3を使用するよう構成される。

2.3. iOSクライアント構成

iPadアプリケーション：最適な性能と優れたユーザー体験を確保するために、iPadデバイス向けに特化して構築されたネイティブiOSアプリケーション。

言語およびフレームワーク：
  • 主要プログラミング言語：Swift
  • UIフレームワーク：UIKit。iPadに合わせた適応的かつ対話的なユーザーインターフェースを構築するために使用される。
アーキテクチャ：

本アプリケーションは、機能ごとの要件に最も適合させるため、ハイブリッドなアーキテクチャアプローチを採用する。
- MVC（Model-View-Controller）：アプリケーションの大部分は古典的なMVCパラダイムに従い、View Controllerがユーザー操作を管理し、Model（データ）とView（UIコンポーネント）の間を調整する。このアプローチは関心の分離を明確にする。
- MVVM（Model-View-ViewModel）：複雑なビジネスロジックまたはデータ変換を要する機能で、MVVMを選択的に使用する。これらの場合、ViewModelクラスが、アプリケーションロジック、データ操作、API準備をカプセル化する。このパターンは、UIコードをビジネスロジックから分離することで、テスト容易性と保守性を向上させる。
- イベント通信：View Controller、カスタムView、ポップアップ間の通信に、委譲（Delegation）パターンが広く使用され、プロトコルベースの抽象化によりモジュール性を促進する。
- UI構成：再利用可能でモジュール化されたインターフェースコンポーネントを作るために、カスタムUIViewサブクラスと合成的デザインが活用される。

ハードウェアおよびOS統合：
  • ハードウェア活用：本アプリケーションは、iPad固有のハードウェアと統合する。これには、署名取得のための描画／手書きを行うApple Pencilサポート、ならびにQRおよびナンバープレートのスキャンのためのカメラが含まれる。
  • OSレベル機能：Split ViewやSlide Overなど、iPadOSのマルチタスク機能をサポートし、ユーザーが他アプリケーションと並行して本アプリを使用できるようにする。
API連携：

本アプリケーションはRESTful APIを介してバックエンドシステムと通信する。
- 通信プロトコル：すべてのネットワークトラフィックを暗号化するためにHTTPSを使用する。
- データ形式：すべてのデータ交換にJSONを使用する。
- APIクライアント：ネットワーキングにはAlamofireを使用する。これは堅牢なHTTPネットワーキングライブラリであり、リクエスト管理やレスポンス処理などのタスクを簡素化する。
- 並行処理モデル：コードベースは、非同期処理にcompletion handlerとGCD（Grand Central Dispatch）を使用する。一部モジュールではSwiftのasync/awaitを活用する場合があるが、主要パターンではない。
- エラー処理：アプリケーションはHTTPステータスコード（例：成功は2xx、エラーは4xx/5xx）を解釈し、ユーザーに適切なフィードバックを提供する。

認証：

本アプリケーションは、保護されたバックエンドリソースへ安全にアクセスするため、トークンベースの認証方式を使用する。
- トークン種別：アクセストークンとしてJWT（JSON Web Token）を使用する。
- 認証フロー：
- ログイン：ユーザーが資格情報をバックエンドのログインエンドポイントへ送信する。
- トークン発行：検証が成功すると、バックエンドはアクセストークンとリフレッシュトークンを返す。
- トークン保存：トークンはiOS Keychainに安全に保存される。
- 認証付きリクエスト：以降、保護されたエンドポイントへのAPIリクエストすべてにおいて、Authorizationヘッダ（例：Bearer ）にアクセストークンを含める。
- トークン管理：トークン有効期限：アクセストークンの有効期限は7日である。

5.1 インターフェース設計 (Web)

Angularフロントエンドは、以下の主要領域に整理されたレスポンシブなWebインターフェースを提供する。

5.1.1. ナビゲーションとダッシュボード

  • メインナビゲーション：モジュールカテゴリとクイックアクセスリンクを備えたサイドメニュー
  • ダッシュボード：主要指標、最近の活動、通知の概要
  • ユーザー操作：ユーザープロフィール、設定、認証管理
  • ルート
  • パス：/dashboard
  • ガード：AuthGuard（認証済みユーザーのみ）
  • 目的
  • コアモジュールおよび頻用アクションへの、役割（ロール）に応じた入口点を提供する。
  • クイックアクセスタイルと一貫した左ナビゲーションにより、タスク到達時間（time-to-task）を短縮する。
  • ロールベースのアクセス
  • モジュールの表示およびアクセスはロールの範囲で制御される。サイドバーはロールごとにモジュールグループを構成する（例：Adminは全て表示、Shopロールは店舗関連モジュール、Factory/Tabletロールは工場カレンダー／予約を表示）。
  • アクセス制御はAuthGuardおよびルートごとのデータ（例：特定の工場ルートにおけるblockedRoles）で強制される。
  • 非許可モジュールはサイドバーから隠され、ディープリンクの試行はブロックされてリダイレクトされる。
  • レイアウト
  • 左サイドバー：アイコン付きでグループ化されたモジュール。長いメニュー向けに折りたたみ可能なグループ。
  • トップバー：言語切替、（該当する場合）ディーラー／店舗コンテキスト選択、ユーザーメニュー（プロフィール／ログアウト）。
  • コンテンツ：ダッシュボードタイル（大きいタッチターゲット（≥44×44px））、アイコン＋ラベル＋短い説明。レスポンシブな2〜4列グリッド、固定（sticky）のページタイトル。
  • クイックアクセスタイル（例）
  • サービス：タブレットアプリで使用されるサービス／商品マスタを管理する。
  • タブレットユーザー：タブレットユーザーの作成／割当、リセット、アクセス管理。
  • 車両：車両管理。
  • 店舗：店舗（SS）の基本設定および管理。
  • 注文履歴：過去注文および詳細の検索・参照。
  • 顧客：顧客管理（許可されたロールにのみ表示）。

注記：表示されるタイルは、サインインユーザーのロールでフィルタされる。

  • 操作と状態
  • タイルクリック：対象機能へ遷移し、ルート変更時にローディングスピナーを表示する。
  • ロール制限：タイルはUIから除外される。ディープリンクされた場合、「アクセス拒否」トーストを表示してリダイレクトする。
  • 空／初回実行：ダッシュボード領域にオンボーディングのヒントを表示する（例：「最初の店舗を追加」）。
  • 国際化
  • すべてのラベルおよびタイル説明は、ngx-translateのdashboard.*キーで提供する。
  • トップバーの言語切替により、タイル文言とサイドバーラベルは即時に更新される。
  • セキュリティ
  • ロールゲーティングはサーバー側およびクライアント側で行われる。UIは制限されたナビゲーションを隠し、ナビゲーション時に認可を検証する。

6.2.1 アーキテクチャ

このセクションは、ネイティブiPadアプリケーションの中核となる技術基盤を概説する。

  • 主要プログラミング言語：Swift
  • UIフレームワーク：UIKit。iPadに合わせた適応的かつ対話的なユーザーインターフェースを構築するために使用される。
  • アーキテクチャパターン：
    • MVC（Model-View-Controller）：アプリケーションの大部分は古典的なMVCパラダイムに従い、View Controllerがユーザー操作を管理し、Model（データ）とView（UIコンポーネント）の間を調整する。このアプローチは関心の分離を明確にする。
    • MVVM（Model-View-ViewModel）：複雑なビジネスロジックまたはデータ変換を要する機能では、MVVMを選択的に使用する。これらの場合、ViewModelクラス（例：BookingRequestViewModel）が、アプリケーションロジック、データ操作、およびAPI準備をカプセル化する役割を担う。このパターンは、UIコードをビジネスロジックから分離することで、テスト容易性と保守性を向上させる。
  • イベント通信：View Controller、カスタムView、ポップアップ間の通信に、委譲（Delegation）パターンが広く使用され、プロトコルベースの抽象化によりモジュール性を促進する。
  • UI構成：再利用可能でモジュール化されたインターフェースコンポーネントを作成するために、カスタムUIViewサブクラスおよび合成的デザインが活用される。
  • 並行処理モデル：コードベースは、非同期処理にcompletion handlerとGCDを使用する。一部モジュールではSwiftのasync/awaitを活用する場合があるが、主要パターンではない。
  • APIクライアント：ネットワーキングは、URLSessionのみを使用するのではなく、堅牢なHTTPネットワーキングライブラリであるAlamofireを使用して実行される。

このセクションは、iOSアプリケーションの全モジュールにわたり実装される、通信、データ取り扱い、およびセキュリティに関する標準的な実務と技術詳細を規定する。

通信プロトコルおよびデータ
  • 通信プロトコル：ネットワーク上で送信されるすべてのデータを暗号化するため、HTTPSを厳格に強制し、クライアントとサーバー間の安全な通信を確保する。
  • データ形式：アプリケーションとサーバー間のデータ交換にはJSON（JavaScript Object Notation）を使用する。
  • HTTPメソッド：標準的なRESTfulメソッドを使用する。GET（取得）、POST（作成）、PUT/PATCH（更新）、DELETE（削除）。
認証
  • アプリケーションは、バックエンドとの間でトークンベースの認証方式を使用する。
  • トークン種別：アクセストークンの作成にJWT（JSON Web Token）を使用する。
  • アクセストークン有効期間：アクセストークンの有効期間は7日である。
  • トークン保存：アクセストークンおよびリフレッシュトークンの両方は、iOSの高セキュリティな保存領域であるKeychainに安全に保存される。
  • 認証付きリクエスト：保護されたAPIへのすべてのリクエストで、Authorization: Bearerヘッダにアクセストークンを含める。
エラー処理（iOS固有）
  • 取り扱い：アプリケーションは、API呼び出しから起こり得るエラーを、標準的なHTTPステータスコード（例：2xx、4xx、5xx）を解釈することで取り扱う。
  • 目的：エラー処理は、技術的でない簡潔なローカライズ（JA/EN）メッセージを提供し、ネイティブiOSのパターン（アラート、バナー）を用い、最小限の妨げで表示するよう設計される。

    - /api/license-plate-reminders/（GET）：

}

]

}

]

}

- is_active=true の場合、同一ディーラー内で同じtypeの有効（active）リマインダーが既に存在してはならない。

  "role": 6,
  "password": "TempPass1!"
}
  • ステータスコード
    • 200 OK：GET, PATCH, DELETE, reset-password 成功
    • 201 Created：POST 成功
    • 400 Bad Request：バリデーションエラー
    • 401 Unauthorized：トークンなし／無効トークン
    • 403 Forbidden：Admin以外
    • 404 Not Found：無効なユーザーID

8. エラー処理

8.1. 認証および認可エラー

  • 目的
    • 明確で非技術的なローカライズメッセージ（JA / EN）を提供する。
    • セキュリティ保護：ユーザー向け表示やログに機密情報を含めない。
    • 信頼性の高いフローを保証する：トークン更新、一貫した 403 ハンドリング。
    • 可観測性を維持する：構造化エラー、traceId、メトリクス、監査ログ。
  • 対象シナリオ
    • ログイン失敗：ユーザー名／パスワード不正時の処理。
    • トークンエラー：期限切れまたは無効トークンの検出。
    • 権限拒否：説明メッセージ付きの適切な 403 レスポンス。
    • ログ：認証試行および失敗をセキュリティ監視用に記録。
  • ログおよび監視
    • ログ項目：timestamp、userId／username ハッシュ、送信元IP、結果、理由コード、traceId。
    • 生パスワードやトークンは絶対にログ出力しない。
    • トークン更新成功／失敗、無効／期限切れイベント、失効を記録する。
  • セキュリティ考慮事項
    • 一定時間比較（constant-time）による資格情報比較。
    • 汎用的な失敗メッセージ（「ユーザーが存在しない」などを出さない）。

8.2. データ検証エラー

  • 目的
    • 不正入力に対し、即時で明確なローカライズメッセージ（JA / EN）を提供する。
    • サーバー側で一貫したスキーマベース検証を強制する。
    • 可観測性のため traceId 付き構造化エラーを返す。
  • 対象シナリオ
    • フォーム検証：クライアント側の即時バリデーション。
    • API検証：詳細なエラーメッセージを伴うサーバー側検証。
    • データ型エラー：型チェックおよび変換エラー処理。
      • 制約違反：DB制約エラーの処理とユーザーフレンドリーなメッセージ。
  • クライアントUX動作
    • インライン検証
      • blur 時および送信時に検証し、各フィールド横にエラー表示。
      • 必要に応じ、必須項目が基本チェックを通過するまで送信を無効化。
    • エラーサマリー
      • 送信失敗時、無効項目数と「最初のエラーへスクロール」操作付きの非技術的バナーを表示。
      • 短く簡潔な文言を使用し、技術用語を避ける。
    • ローカライズ
      • 既定は日本語。メッセージは catalog または message_i18n から取得。
  • サーバー検証ポリシー
    • 業務ロジック前にスキーマ／アノテーションフレームワークでリクエスト検証。
  • ログおよび監視
    • ログ：コード、ステータス、traceId、ルート。
    • エンドポイント／フィールド別の検証失敗率をメトリクスとして追跡。
    • UI退行や不正クライアントを示すスパイク検知でアラート。

8.3. インポート／エクスポートエラー

  • 目的
    • ファイル／行単位の問題に対し、明確でローカライズされたメッセージ（JA / EN）を提供する。
    • 早期かつ深い検証（クライアント事前チェック、サーバースキーマ、DB制約）。
    • ImportResult／ExportResult によるエラー追跡。
  • 対象シナリオ
    • ファイル形式エラー：不正形式検出と具体的エラーメッセージ。
    • データ検証：行単位検証とエラー報告。
    • 処理エラー：ImportResult／ExportResult オブジェクトでの追跡。
    • 復旧手段：部分インポート、エラー修正ワークフロー。
  • クライアント／UX動作
    • アップロード前チェック：送信前に型とサイズを検証。
    • 進捗／バックグラウンド処理：進捗表示。大規模インポートはバックグラウンドジョブ＋ ImportResult.id によるポーリング。更新用リフレッシュボタンを提供。
    • 行単位レポート：テーブル形式でエラー表示、フィルタ可能。「エラーCSVダウンロード」（行、フィールド、コード、メッセージ）。
    • ローカライズ：既定は日本語。全テキストは i18n catalog または message_i18n から取得。
  • サーバー処理ポリシー
    • ストリーミング：大容量ファイルは O(row) でストリーム解析し、メモリスパイクを防止。500行単位でバッチ書き込み。
    • 検証：行エラーを収集。
    • エクスポート：キュージョブ使用、タイムアウト、再開／再試行可能。
  • ログおよび監視
    • ジョブ単位ログ：件数（合計／成功／失敗）、主要エラーコード、所要時間、traceId。
    • メトリクス：インポート失敗率、平均行エラー率、エクスポート失敗、キュー遅延。

8.4. ネットワークおよび通信エラー

  • 目的
    • ネットワーク問題に対し、明確でローカライズされたユーザーフィードバック（JA / EN）を提供する。
  • 対象シナリオ
    • タイムアウト処理：適切な設定とユーザー通知。
    • 接続問題：ネットワーク異常の検出と通知。
    • エラーレスポンス：HTTPステータスと詳細を含む構造化レスポンス。
  • タイムアウトポリシー
    • クライアント
      • 接続タイムアウト、全体リクエストタイムアウト：[30秒]
      • クライアント側タイムアウト演算子を適用し、期限切れ時にユーザーメッセージ表示。
    • サーバー
      • クライアント合計より短い上流タイムアウトで連鎖待ちを防止。
      • 408／504／503 を一貫して返却。
  • 接続検知およびUX
    • オフライン時は非技術的文言と再試行操作付きの常時バナーを表示。
  • ログおよび監視
    • ステータス別件数（408／429／502／503／504）を集計。

8.5. iOS 固有のエラー処理

  • 目的
    • 非技術的で簡潔、ローカライズ（JA / EN）されたメッセージを提供する。
    • 最小限の妨げで、iOS標準UI（アラート、バナー、シート）を使用する。
    • アクセシビリティ、マルチタスク安全性、可観測性を確保する。
  • 対象範囲
    • ネットワーク／オフライン、タイムアウト、サービス停止、認証／セッション、OS権限（カメラ／写真／ファイル）、共有／印刷、QR、長時間処理。
  • 原則
    • 短く、行動可能なメッセージ。
    • 継続状態（オフライン）は常時UI、短期通知は一時UI。
    • 技術詳細は表示しない（診断はログのみ）。
    • 全ユーザー向け文言をローカライズ（既定JA、EN提供）。
  • 表示パターン（iOS）
    • バナー（非ブロッキング）：オフライン等の継続状態。
    • アラート／確認ダイアログ：ユーザー判断が必要な場合。
    • インライン：ビューに紐づく入力／内容エラー。
  • 重要度 → UI マッピング
    • Info：軽量バナー（3～5秒で自動消去）。
    • Warning：閉じる／再試行付きバナー。
    • Error：主要操作付きアラートまたはシート。

8.6. システムおよびインフラエラー

  • 目的
    • 安定性：早期失敗、影響範囲の局所化、サービス応答性維持。
    • 明確性：非技術的ユーザーメッセージ、詳細な内部診断。
    • 追跡性：サービス横断で traceId を含む構造化エラー。
    • 可観測性：ログ、メトリクス、トレーシング、実用的アラート。
  • 対象シナリオ
    • サーバーエラー（500）：未処理例外、設定不備、リソース枯渇。
    • DBエラー：コネクション枯渇、タイムアウト、デッドロック、制約マッピング。
    • 外部サービス障害：タイムアウト、5xx、サーキットブレーカー開放。
    • 監視／アラート：エラー集約、閾値、オンコール。
  • 耐障害性／復旧ポリシー
    • Sentry や CloudWatch のエラーログを確認し、修正パッチを適用。
  • DBエラーハンドリング
    • 接続問題：ヘルスチェックで劣化状態を通知し、DB.CONNECTION_FAILED（503）を返却。
    • クエリ失敗：クエリ名とパラメータ（秘匿化）をログし、500を返却。
    • 制約マッピング：検証エラー／409 として返却。
クライアント向け挙動
  • ユーザーメッセージ：非技術的。後で再試行を促す。
ログ／監視／アラート
  • 構造化ログ：JSON（level、code、traceId、service、endpoint、latencyMs）。
  • メトリクス：5xx率、依存障害率、サーキットブレーカー状態、DBプール飽和、キュー深度。
  • トレーシング：traceId をサービス間で伝播。
ヘルスチェック／レディネス
  • Liveness：基本プロセス健全性。失敗時はメール通知。

9. セキュリティ設計

9.1. データ暗号化および保護

  • 目的
    • 通信中（TLS）および保存時（DB、S3/KMS）の暗号化。
    • 強力な鍵管理とローテーション。
    • ハードコードされた秘密情報を排除し、集中管理。
  • 標準およびポリシー
    • 通信：全通信で HTTPS 強制。HSTS（preload）有効化。
    • 保存時（DB）：django-searchable-encrypted-fields（AES-256-GCM）で機微PIIを暗号化。
    • ファイル：S3 SSE-KMS。非TLSおよび公開ACLを拒否するバケットポリシー。プリサインURLは短命。
    • 鍵管理：環境変数／シークレットマネージャーから取得し、定期ローテーション。
    • シークレット：コードやデフォルトに含めない。リポジトリを監査。
  • データ分類
    • 暗号化対象PII：顧客名、メール／電話、VIN（必要に応じ）、住所、PIIを含むメモ。

9.2. 認証メカニズム

  • 目的
    • JWTによるステートレス認証。
    • レート制限とロックアウトによるログイン保護。
    • iPad での安全なトークン保存（Keychain）。
  • 標準およびポリシー
    • アクセストークンTTL：7日。
    • 常に Authorization: Bearer <token を使用。
    • パスワード変更や不審挙動時にトークン失効。
  • 防御
    • レート制限：ログイン試行をスロットリング。10回失敗でロックアウト＋クールダウン。
  • iOS（ネイティブアプリ）保存
    • アクセストークンはメモリ上のみ保持。

9.3. 認可およびアクセス制御

  • 認可モデル
    • 認可はすべての API リクエストに対して順番に適用される 4 層で実施される。リクエストはすべての該当レイヤーを通過する必要がある。
    • レイヤー順：認証（Authentication）→ RBAC → メニュー／パーミッションアクセス → スコープ（BOLA）。
  • Layer 1：認証（Authentication）― あなたは誰か？
    • リクエストが有効な JWT を持ち、呼び出しユーザーを特定していることを検証する。有効な認証情報がないリクエストは HTTP 401 で拒否される。
  • Layer 2：RBAC ― あなたのロールはこのエンドポイントに許可されているか？
    • 各エンドポイントはアクセスを許可されるロールを宣言する。
    • 許可リスト（推奨）：明示的にリストされたロールのユーザーのみ許可。それ以外は HTTP 403。
    • 拒否リスト（レガシー）：リストされたロールはアクセス拒否。後方互換性のため少数のエンドポイントで維持。
    • メソッド・アクション別のバリアントをサポート（例：あるロールは読み取り専用、別のロールはフルアクセス）。
  • Layer 3：メニュー／パーミッションアクセス ― この細粒度パーミッションを持っているか？
    • ロールメンバーシップを超えて、文字列キー（"pkey"）で識別される細粒度パーミッションをサポート（例：settings.shop_information_settings.user_profiles）。
    • ロールパーミッション：特定のディーラー（または Branch Admin の場合は支店）のスコープ内でロールに付与される。
    • ユーザーパーミッション：ロールのデフォルトに重ねて、パーミッションを明示的に許可または拒否するユーザー単位のオーバーライド。
    • 有効パーミッション：（ロールパーミッション ∪ ユーザー許可オーバーライド）― ユーザー拒否オーバーライド として解決される。
    • 適用対象：Branch Admin、Dealer Manager、Shop Manager、Shop。その他のロールはこのレイヤーをバイパス。
  • Layer 4：スコープ／BOLA ― その特定のオブジェクトを所有しているか？
    • BOLA（Broken Object-Level Authorization）を防止：ロールおよびパーミッションチェックを通過した後も、ユーザーはアクセスしようとする特定のオブジェクトを所有またはスコープされている必要がある。
    • ロール別のデフォルトスコープルール：
      • Dealer 一致：オブジェクトの dealer はユーザープロフィールの dealer と一致しなければならない。
      • Shop 一致：オブジェクトの shop はユーザープロフィールのアサインされた shops のいずれかでなければならない。
      • Admin：常にスコープチェックをバイパス。
    • スコープはリクエストライフサイクルの複数の箇所で適用：クエリセットフィルタリング（get_queryset）、オブジェクト取得（get_object）、シリアライザー外部キー検証、ミューテーション事前チェック、監査ログ。
  • DRF実装
    • 既定：IsAuthenticated。
    • カスタム権限クラス：
      • HasRole(role_or_higher)
      • IsDealerMember / IsBranchMember / IsShopMember
      • ObjectBelongsToUserOrg
    • get_queryset で組織スコープ適用。
  • API認可チェックリスト
    • 全エンドポイントに明示的 permission_classes。
    • get_queryset で行レベルフィルタ。
    • 更新／削除前に所有権（dealer／shop）検証。
    • Admin のオーバーライドは許可し、監査。

9.4. 入力検証およびサニタイズ

  • 目的
    • DRFシリアライザとカスタムバリデータによる強固な検証。
    • 入力の正規化／サニタイズ、XSS／インジェクション防止。
    • アップロード検証（型／サイズ／内容）と危険コンテンツ拒否。
  • 検証基準
    • 全エンドポイントで DRF シリアライザを使用。
    • 構文／型エラーは 400 を返却（例外ハンドラで一貫マッピング）。
    • ファイルアップロード：MIME／拡張子／最大サイズ、CSV/XLSX ヘッダ検証。

9.5. API セキュリティおよびインフラ保護

  • 目的
    • 一般的な脆弱性や DDoS 攻撃への防御。
    • インフラ間通信の安全性確保。
    • 監査証跡の維持。
  • 標準およびポリシー
    • DDoS 対策：Cloudflare によるエッジでの緩和、レート制限、悪性トラフィック遮断。
    • WAF：Cloudflare WAF（SQLi、XSS、HTTP Flood 対策）。
    • CDN／プロキシ：Cloudflare をリバースプロキシとして使用し、オリジン隠蔽。
    • コンテナセキュリティ：Amazon Inspector による定期脆弱性スキャン。
    • ネットワークセキュリティ：
      • 最小権限のセキュリティグループ。
      • アプリ／DB はプライベートサブネット。
      • DB はインターネット非公開。

9.6. 監視、ログ、インシデント対応

  • 目的
    • 包括的なセキュリティ監視とアラート。
    • コンプライアンス／フォレンジックのための監査証跡。
    • インシデント対応手順の確立。
  • 標準およびポリシー
    • アプリケーションログ：相関ID付き構造化ログ。PIIは除外。
    • セキュリティ監視：
      • CloudWatch アラート（不審挙動）
      • Cloudflare Analytics／Security Events
      • RDS クエリログ有効化
    • S3 アクセスログ有効化
  • 監査証跡：
    • AWS CloudTrail
    • Cloudflare Access ログ
    • Django 管理画面操作ログ
    • ユーザー認証／権限変更ログ
  • インシデント対応：文書化された手順、定期バックアップ検証。
